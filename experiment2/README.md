# UI 인식 vs AI 궤적 예측 비교 실험 (phase 1: UI 인식)

`experiment/`(v1 WebGazer, v2 MediaPipe)에서 웹캠 시선추적을 실측한 결과 머리 자세
변화에 취약해 구역 판별조차 불안정했다. 그래서 이번 비교에서는 **시선추적을 뺀다**.
대신 두 접근을 비교한다.

- **UI 인식**: 클릭 시점에 후보 버튼 중 가장 가까운 버튼 하나를 고른다(DOM `getBoundingClientRect`).
- **AI(궤적 학습)**: 클릭 직전 구간의 마우스 이동 궤적(시계열)으로 의도 버튼을 예측한다. *(phase 2, 미구현)*

## 가설

버튼이 떨어져 있는 **일반 배치(A)**에서는 UI 인식(최근접 규칙)이 잘 맞고,
브라우저 북마크바처럼 버튼이 **다닥다닥 붙은 밀집 배치(B)**에서는 최근접 규칙만으로는
후보가 애매해져(동률·근소한 오차로 오분류) 정확도가 떨어질 것이다. 이 지점에서
궤적의 진행 방향 같은 정보를 쓰는 AI가 UI 인식보다 유리할 것으로 예상한다.

phase 1은 이 가설의 전반부(UI 인식이 A에서 잘 되고 B에서 무너지는가)를 실제로
측정하는 단계다. AI와의 비교는 그 다음이다.

## phase 1 — UI 인식 (이번에 구현한 것)

### 알고리즘
`app.js`의 `recognizeUI(point, buttons)`: 클릭 좌표에서 각 버튼 사각형까지의
거리(점이 사각형 안이면 0)를 계산해 최소인 버튼 하나를 고른다. **반경 제한 없음** —
항상 하나를 고른다(이전 `experiment/`의 `snapRadius` 컷오프는 제거).

**동률 판정은 고정 임계값을 쓰지 않는다.** 처음엔 1·2위 거리차 0.5px 미만을
동률로 봤는데, 밀집 배치에서도 사람이 "사실상 애매하다"고 느끼는 거리차는
그보다 훨씬 클 수 있어(수 px~십몇 px) 고정값으로는 실제 동률 상황 대부분을
놓친다. 그래서 지금은 1위·2위 거리(`recDist`, `secondRecDist`)와 그 차이
(`distGap`)를 매 시행 원본 그대로 저장하고, 몇 px 이하를 동률로 볼지는 결과
화면의 "동률 판정 임계값" 입력칸에서 분석 시점에 자유롭게 바꿔볼 수 있게 했다.

**안전성(오보정)은 phase 1에서 의도적으로 안 본다.** C-UI가 반경 제한 없이
항상 최근접 버튼을 고르는 건 순수 판별력만 보려는 선택이고, "표적에서 한참
벗어난 클릭을 억지로 아무 버튼에나 갖다 붙이는" 위험은 이 실험이 측정하지
않는다. 역효과율이 안전성의 일부를 대리하긴 하지만 전부는 아니라는 점을
결과 화면에도 명시해뒀다.

**역효과율 정의도 한 번 고쳤다.** 처음엔 "원클릭이 표적을 직접 맞혔는데
보정이 다른 버튼으로 틀어버린 비율"로 정의했는데, 버튼이 서로 안 겹치는
배치에서는 이게 논리적으로 절대 발생할 수 없었다 — 원클릭이 표적 안이면
`recognizeUI`가 계산하는 표적까지 거리가 항상 0이고, 안 겹치는 다른 버튼은
같은 점에서 거리가 항상 0보다 크므로 표적이 무조건 유일한 최솟값이 되기
때문이다. 즉 그 정의로는 역효과율이 구조적으로 항상 0%였다.

지금 정의(사용자 확정): **원클릭이 애초에 어떤 버튼 안에도 없었는데(클릭
자체가 실패), 보정이 그걸 표적이 아닌 다른 버튼으로 확정해서 눌러버린
비율.** "클릭 실패"보다 "엉뚱한 버튼을 확신 있게 눌러버림"이 더 나쁘다는
기준이고, 이건 구조적으로 막혀 있지 않아 실제로 관측 가능하다.

### 두 시나리오
- **A. 일반 배치**: `experiment/` v1의 target+distractor 배치(버튼 간 여백 있음)를 그대로 이식.
- **B. 밀집 배치(북마크바형, 신규)**: 작은 버튼 12개를 화면 상단에 간격 거의 없이
  한 줄로 붙여 놓고 그중 하나가 표적. `layoutDense()`.

두 시나리오 모두 내부적으로 `{home, target, distractors}` 같은 구조로 반환되어
채점·로깅 파이프라인을 공유한다 — 시나리오별로 로직을 분기할 필요가 없다.

### 조건
- `C0` 보정 없음 (기준선)
- `C-UI` UI 인식(최근접 스냅, 항상 적용)

### 핵심 측정 지표 (결과 화면)
조건 간 명중률·오차 비교뿐 아니라, **역효과율**(원클릭은 아무 버튼도 못 맞혔는데
UI 인식이 표적이 아닌 다른 버튼을 확정해 눌러버린 비율)과 **동률률**(임계값은
결과 화면에서 조절 가능)을 시나리오별로 따로 낸다. 가설이 맞다면 밀집 배치(B)에서
이 두 지표가 일반 배치(A)보다 뚜렷이 높게 나와야 한다 — 이게 phase 2(AI)가
필요하다는 실증적 근거가 된다.

### 표본 수(N) 배분
밀집 배치(B)에서의 역효과·동률은 드물게 나오는 사건일 수 있어, 일반 배치(A)보다
반복 수를 더 많이 배분한다(기본값: A=2, B=4, 메뉴에서 조절 가능).

### 시간압박을 눈에 보이게
`timeLimitMs`(기본 900ms) 제한이 있는 시행에서는 화면 상단에 막대가 제한시간
동안 0→100%로 차오른다. 클릭하고 나서야 시간 초과 여부를 알게 되면 긴장감이
없다는 지적을 반영해, 차오르는 막대를 보면서 다 차기 전에 눌러야 하는 실제
압박을 주도록 했다(`app.js` `showTarget()`, `index.html` `#timeBar`).

## 데이터 로깅 (phase 2 대비)

매 시행마다 `trial.traj`에 클릭 직전 구간의 원본 마우스 궤적을
`[{x, y, t}]`(브라우저 `mousemove` 네이티브 발생 빈도, `performance.now()` 타임스탬프)
그대로 저장한다. **고정 간격 리샘플링과 클릭 전 구간 자르기는 지금 하지 않는다** —
원본에 타임스탬프가 있으니 나중에 학습 시점에 보간(resample)하면 되고, 지금 미리
자르면 나중에 윈도우 길이를 바꿔보고 싶을 때 데이터를 다시 모아야 한다.

## phase 2 계획 — AI (미구현, 다음 단계)

방향(사용자 확정):
- **머신러닝**: 이번 실험에서 모으는 데이터로 처음부터 학습. 입력은 클릭 직전
  구간을 고정 간격으로 리샘플링한 (x, y) 시계열(또는 거기서 뽑은 속도·진입각 등
  특징), 출력은 의도 버튼(또는 보정 좌표).
- **딥러닝**: 데이터를 대량으로 모으기 어려우므로 처음부터 학습하지 않는다.
  기존에 존재하는 유사한(궤적/제스처 계열) 사전학습 모델을 가져와 이 실험에서
  모은 사용자 데이터로 파인튜닝하는 방식을 검토한다. *(어떤 사전학습 모델을 쓸지는
  아직 미정 — 마우스 궤적 전용 공개 사전학습 모델이 실제로 있는지부터 확인 필요.
  없다면 여러 참가자 데이터를 모아 자체적으로 "사전학습"에 준하는 것을 만들고
  개인별로 파인튜닝하는 대안도 고려.)*
- **클릭 전 구간만 사용**: 궤적 전체를 넣으면 이동 시작 시점의 목적 없는 움직임이
  섞여 들어가므로, 클릭 시점 기준으로 일정 구간만 잘라 사용한다. 구체적인 길이는
  아직 정하지 않았고, phase 1에서 쌓이는 `mt`(이동시간) 분포를 보고 정하는 게
  합리적이다(예: 중앙값의 절반 정도, 혹은 마지막 N ms).

## 실행

```bash
cd experiment2
python -m http.server 8733
```
브라우저에서 <http://localhost:8733> 접속. 웹캠 불필요 — `file://`로 직접 열어도 된다.
