## v1(WebGazer) vs v2(MediaPipe) — 뭐가 다른가

| | v1 · WebGazer | v2 · MediaPipe Face Landmarker |
|---|---|---|
| 나온 시기 | 2016년, Brown University | 구글, 지속 관리 중 |
| 방식 | 눈 주변 **픽셀 이미지**를 그대로 릿지 회귀에 입력 | 얼굴 478개 3D 랜드마크(눈동자 포함)를 먼저 추출 → **기하학적 특징**을 계산해 그 특징으로 회귀 |
| 머리 자세 인식 | 없음. 보정 시점 자세가 곧 모델의 암묵적 기준이 됨 | 코끝 위치·눈 간격(거리 근사)·좌우 눈 폭 비율(회전 근사)을 특징에 명시적으로 포함 |
| 머리 움직임에 대한 강건성 | 약함 — 자세가 바뀌면 예측이 크게 틀어짐 (이번에 실측한 문제) | v1보다 나을 것으로 기대(가설). 완전한 3D 시선벡터 추정은 아니라서 한계는 여전히 있음 |
| 회귀 구현 | WebGazer 라이브러리 내장(블랙박스, 버전별 거동 차이 있었음 — showPredictionPoints 등 토글이 씹히는 문제 등) | 이 프로젝트에서 직접 구현한 릿지 회귀(`fitRidge`, `solveLinearSystem`, app.js 3a절). 특징 정규화(z-score) 후 학습 |
| 비용/라이선스 | 무료, BSD-3-Clause | 무료, Apache-2.0. 서버·API 키 없음, 100% 브라우저 로컬 실행(WASM) |
| 보정 UI | 9점 × 5클릭 (동일) | 9점 × 5클릭 (동일) — 클릭 순간 특징 벡터를 화면 좌표와 짝지어 표본으로 저장 |
| 다운스트림(구역 판별·보정 로직·분석) | `App.gazeBuffer`에 `{x,y,t}`만 쌓으면 나머지는 동일 | 동일 — `Gaze.dominantZone()` 인터페이스가 같아서 v1의 시행/보정/분석 코드를 그대로 재사용 |

## 특징 벡터 (app.js `featuresFromLandmarks`)

프레임마다 8차원 벡터를 계산합니다.

1. 눈 A(왼쪽) 안에서 눈동자의 상대 위치 (dx, dy)
2. 눈 B(오른쪽) 안에서 눈동자의 상대 위치 (dx, dy)
3. 코끝의 정규화 좌표 (x, y) — 머리 위치·회전 대략적 반영
4. 두 눈동자 사이 거리 — 카메라와의 거리 근사(가까울수록 큼)
5. 좌우 눈 폭 비율 — 고개를 좌우로 돌리면 한쪽이 원근 때문에 짧아짐 → 회전 근사

보정 시 45(≤)개 표본에 대해 이 특징들을 z-score 정규화한 뒤, 화면 x좌표용/y좌표용 릿지 회귀를 각각 학습합니다(λ=3.0).

## 알려진 한계 (v1과 공통)

- 그래도 완전한 3D 시선벡터 추정(딥러닝 gaze estimation)은 아닙니다. 여전히 "구역 단위" 정확도를 목표로 설계돼 있습니다.
- 표본이 45개뿐이라(참가자당) 과적합 방지를 위해 특징을 8차원으로 제한하고 릿지 정규화를 걸었습니다 — 더 정교한 모델(고차항, 딥러닝)을 쓰려면 표본이 훨씬 더 많이 필요합니다.
- 저는(Claude) 웹캠에 접근할 수 없어 실제 동작을 직접 테스트하지 못했습니다. 처음 실행 시 v1 때처럼 몇 차례 디버깅이 필요할 수 있습니다.

## 비교 실험 시 주의

- `localStorage` 키를 v1(`mc_trials`)과 다르게 `mc_trials_v2`로 분리해서 두 버전 데이터가 섞이지 않습니다.
- 같은 참가자로 v1·v2 예비실험 A를 각각 돌려서 구역 판별 정확도를 직접 비교해보는 걸 추천합니다 — 이게 "WebGazer보다 나은가"에 대한 실제 답이 됩니다.
