## 1. 저장 방식 2안

|---|---|---|---|
| **A. 로컬 실행** | ✗ (다운로드 폴더) | 최하 | 8명을 한 PC에 모을 때 |

### 권장

**8명을 한 PC에 모을 수 있으면 A.** 지금처럼 `python -m http.server`로 열면 그 PC 다운로드 폴더에 JSON 8개가 쌓인다. 인터넷도, 배포도, 토큰도 필요 없다. 게다가 마우스·화면이 자동으로 통제되는데 이게 이 연구에서는 편의 문제가 아니라 타당도 문제다(§7). 25분 × 8명 = 3시간 반.

**원격이 불가피하면 B.** 아래는 B 기준이다. A로 갈 거면 §3만 빼면 그대로 쓸 수 있다.

## 2. 시스템 구성 (B안)

```
[참가자 브라우저]
   Gradio Space
   ├─ 실험 화면 = 순수 HTML/JS  (Gradio 컴포넌트 아님)
   └─ 숨긴 텍스트박스 → 파이썬으로 결과 전달
        │
        ▼
[Space 서버] app.py
   huggingface_hub.upload_file()
        │
        ▼
[HF Dataset repo (private)]  ← 여기가 안 날아가는 저장소
        │
        ▼
[연구자] 8개 한꺼번에 다운로드
```

### 왜 실험 화면을 Gradio 컴포넌트로 못 만드나

| 필요한 것 | Gradio 컴포넌트 |
|---|---|
| 마우스 궤적 125Hz 기록 | ✗ 이동 이벤트를 노출하지 않음 |
| 클릭 좌표를 px 단위로 | ✗ 버튼이 눌렸는지만 전달 |
| ms 단위 타이밍 | ✗ 서버 왕복 지연이 섞임 |
| 전체화면 제어 | ✗ |

**Gradio는 껍데기 + 저장 담당이고, 실험 로직은 전부 JS다.** 기존 `experiment/app.js`를 거의 그대로 재활용할 수 있다.

### 왜 Dataset repo가 필요한가

Space 파일시스템은 재시작하면 초기 상태로 돌아간다. Space는 놀리면 자고, 코드를 고치면 재빌드되고, 가끔 알아서 재시작한다. 서버 안에 그냥 쓰면 데이터가 사라진다.

## 3. 서버 저장 구현

### 3.1 준비

1. HF에서 **private Dataset repo** 생성 (예: `계정/mouse-exp-data`)
2. Settings → Access Tokens → **write 권한** 토큰 발급
3. Space → Settings → Variables and secrets → `HF_TOKEN`으로 등록

### 3.2 app.py

```python
import os, json, datetime
import gradio as gr
from huggingface_hub import HfApi

REPO = "계정/mouse-exp-data"
HTML = open("static/experiment.html").read()
JS   = open("static/experiment.js").read()
CSS  = open("static/experiment.css").read()

def save(payload: str):
    if not payload:
        return "⚠ 전달된 데이터가 없습니다"
    data = json.loads(payload)
    pid  = "".join(c for c in str(data["participant_id"]) if c.isalnum() or c in "_-")
    ts   = datetime.datetime.now().strftime("%Y%m%d_%H%M%S")
    name = f"{data['mode']}_{pid}_{ts}.json"
    path = f"/tmp/{name}"

    with open(path, "w", encoding="utf-8") as f:
        json.dump(data, f, ensure_ascii=False)

    HfApi().upload_file(
        path_or_fileobj=path,
        path_in_repo=f"raw/{name}",
        repo_id=REPO,
        repo_type="dataset",
        token=os.environ["HF_TOKEN"],
    )
    return f"저장 완료 — {pid}, {len(data['trials'])}시행"

with gr.Blocks(head=f"<style>{CSS}</style><script>{JS}</script>") as demo:
    gr.HTML(HTML)
    payload = gr.Textbox(elem_id="payload", visible=False)
    trigger = gr.Button(elem_id="trigger", visible=False)
    status  = gr.Markdown()
    trigger.click(save, inputs=payload, outputs=status)

demo.launch()
```

`참가자 ID`를 그대로 파일명에 쓰면 안 된다. 위 `isalnum` 필터가 그 방어다.

### 3.3 JS → 파이썬 전달

```javascript
function submitResults(data) {
  const box = document.querySelector("#payload textarea");
  const setter = Object.getOwnPropertyDescriptor(
    window.HTMLTextAreaElement.prototype, "value").set;
  setter.call(box, JSON.stringify(data));          // ← 중요
  box.dispatchEvent(new Event("input", { bubbles: true }));
  document.querySelector("#trigger").click();
}
```

**`setter.call`을 쓰는 이유**: `box.value = ...`로 직접 넣으면 React가 변경을 감지하지 못해 파이썬으로 **빈 문자열이 넘어간다.** 오류도 안 나고 조용히 실패한다. 이 한 줄 때문에 며칠 날리는 경우가 흔하다.

### 3.4 실패해도 실험은 건진다

업로드가 실패해도 25분짜리 세션을 날려선 안 된다. 참가자를 다시 부를 수 없다.

```javascript
submitResults(results);
showDownloadButton(results);   // 성공 여부와 무관하게 항상 표시
```

토큰 만료, repo 이름 오타, 네트워크 끊김 — 뭐 하나 틀리면 통째로 사라진다. 다운로드 버튼은 보험이 아니라 필수다.

### 3.5 용량

시행당 궤적이 약 75샘플, 620시행이면 JSON이 1~2MB다. 궤적을 객체 배열 대신 숫자 배열로 저장하면 절반 이하가 된다.

```javascript
// ✗ [{t:0,x:720,y:650}, ...]   약 30바이트/샘플
// ✅ [[0,720,650], ...]         약 14바이트/샘플
```

좌표는 소수점 첫째 자리까지 반올림.

## 4. 실험 설계

### 4.1 고정 조건

| 항목 | 값 |
|---|---|
| 버튼 크기 | **1종 고정** (예비실험에서 결정, 12px 내외 예상) |
| 이동 거리 | **450px 고정** |
| 방향 | 4방향 (↑↓←→) |
| 시간 제한 | 750ms (초과 시 플래그만, 3000ms에 무응답) |
| 버튼 모양 | 원형 (성공 = 중심에서 반지름 이내) |
| 좌표계 | **화면 x/y 그대로** (회전 없음) |

크기·거리를 여러 개 두지 않는 이유: test01은 400회를 48칸(8방향×2거리×3크기)에 나눠 칸당 8회였다. 오차 SD가 5.5px이니 8회 평균의 표준오차가 1.9px, 재려는 편향은 1.3px. 처음부터 측정 불가능한 해상도였다. 조건을 4칸으로 줄이면 같은 400회가 칸당 100회, 표준오차 0.55px이 된다.

### 4.2 두 모드

**모드 A — 크기 정하기 (2~3명만)**

- 워밍업 10회 + 본시행 100회 (후보 8/12/16/24/32px × 각 20회, 무작위)
- 로지스틱 회귀 `logit(성공) = a + b·ln(크기)` → **성공률 65% 지점 크기 1개**
- 이 값을 전원 공통 적용

> 65%로 낮게 잡는 이유: test01의 편향은 1.3px이었다. 반폭 15px 버튼에서 1.3px 밀어봐야 성공/실패가 안 바뀐다. 버튼이 오차만큼 작아야 보정이 승패를 가른다.

**모드 B — 본실험 (8명 전원)**

- 워밍업 20회 + 본시행 600회 (4방향 × 150회, 순서 무작위)
- **앞 400회 = 학습, 뒤 200회 = 평가.** 참가자에게 알리지 않고 화면상 구분도 없다.
- 100회마다 휴식 화면 (참가자가 직접 재개)
- 약 25분, **반드시 한 세션에** (§7)

### 4.3 한 시행

```
1. 화면 중앙에 시작 버튼(30px 고정)
2. 참가자가 클릭             ← 커서 시작 위치 확정
3. 450px 떨어진 4방향 중 하나에 목표 버튼 등장 (t0)
4. 이동 → 클릭
5. 좌표·시각·궤적 기록
6. 200ms 공백 → 다음
```

- `t_click − t0 > 750ms` → `timeout: true` 플래그만. **시행은 유지한다.** 제외하면 신중한(느린) 시행만 빠져 편향 추정이 왜곡된다.
- 3000ms 무클릭 → `no_response: true`, 폐기.
- 궤적은 `mousemove`를 전부 기록. `event.clientX/clientY` (CSS px).

> 궤적은 이번 분석에 **쓰지 않는다.** 그래도 기록은 남긴다 — 보고서에 "궤적 기반 예측도 시도했으나 설명력이 3%였다"를 쓸 재료이자, 나중에 다시 볼 여지다.

## 6. 분석 (수집 완료 후, 로컬 파이썬)

### 6.1 벡터

```python
# 각자 앞 400회(워밍업·무응답 제외)의 평균 오차 벡터
vectors = {p: (mean(err_x[p]), mean(err_y[p])) for p in participants}
```

### 6.2 세 조건 (뒤 200회)

| | 적용 |
|---|---|
| **A** 보정 없음 | 클릭 좌표 그대로 |
| **B** 남의 편향 | 클릭 − (본인 제외 7명 벡터의 평균) |
| **C** 본인 편향 | 클릭 − 본인 벡터 |

```python
for p in participants:
    own    = vectors[p]
    others = mean([vectors[q] for q in participants if q != p])
    test   = trials[p][400:]
    A = test
    B = [c - others for c in test]
    C = [c - own    for c in test]
    # 각각 |좌표 − 목표중심| < 반지름 인지 세기
```

**B를 "본인 제외 7명 평균"으로 잡는 이유**: 한 명만 빌리면 하필 그 사람이 비슷하냐 아니냐로 결과가 흔들린다. 7명 평균이면 "사람들의 공통 편향"이라는 뜻이 분명해지고, B와 C의 차이가 정확히 **개인차 몫**이 된다.

### 6.3 검정

- **주 지표: 성공률.** Cochran's Q (3조건) → 유의하면 사후 McNemar + Bonferroni
- 보조: 오차 거리, 반복측정 ANOVA
- 주 지표는 데이터를 보기 **전에** 확정해 문서에 적어둘 것

### 6.4 결론

| 결과 | 해석 |
|---|---|
| C > A **그리고** C > B | 보정이 되고, 개인화가 필요하다 ✅ |
| C > A **인데** C ≈ B | 보정은 되지만 개인화는 무의미 — 다들 같은 방향으로 치우친다 |
| C ≈ A | 안 된다 ❌ |

세 갈래 모두 결론이다. ❌도 보고 가치가 있다 — 연구계획서 1장의 전제가 틀렸다는 뜻이니까.

## 7. 통제 사항

데이터 품질이 여기서 갈린다.

- **가능하면 같은 PC, 같은 마우스로 8명 전원.** DPI·가속·감도가 다르면 "개인 편향"에 장비 차이가 섞인다. 이 연구의 주장이 개인차인데 그게 오염된다.
- **트랙패드 금지.** 편향 특성이 근본적으로 다르다. 섞으면 8명이 사실상 두 집단이 된다.
- **마우스 가속(포인터 정밀도 향상) 끄기.**
- **브라우저 확대율 100%.**
- **전체화면 필수.** 주소창 높이가 좌표에 섞인다.
- **학습 400회와 평가 200회를 한 세션에.** test01은 1단계와 2단계 사이에 성공률이 73%→65%로 떨어졌다(세션 간 컨디션 차이). 나눠 하면 그대로 재현된다.

시작 화면에서 자동 점검하고, 통과 못 하면 시작을 막는다:

| 검사 | 기준 |
|---|---|
| 창 크기 | `innerWidth ≥ 1200`, `innerHeight ≥ 800` |
| 확대율 | 100% (`outerWidth/innerWidth`로 추정) |
| 입력 장치 | 참가자가 "마우스/트랙패드" 직접 선택, 트랙패드면 경고 |

## 8. 구현 순서

1. **실험 화면 JS 완성** — 로컬 `python -m http.server`로. Gradio는 나중에.
2. **`?dev=1` 축소 모드** (20회). 없으면 점검할 때마다 600번 클릭하게 된다.
3. **스키마 확정 → 더미 데이터로 §6 분석 스크립트를 먼저 돌려본다.** 분석이 안 돌아가는 스키마를 실험 다 하고 발견하는 게 최악이다.
4. Gradio 껍데기 + Dataset 업로드 연결 (§3)
5. Space 배포, 토큰 등록
6. **본인들 둘이 각각 600회 완주** → Dataset repo에 파일이 쌓이고 §6에 그대로 들어가는지 확인
7. 예비실험(모드 A) 2~3명 → 버튼 크기 확정
8. 본실험(모드 B) 8명

**6번을 건너뛰지 말 것.** 참가자 8명 모아놓고 버그를 발견하면 되돌릴 수 없다.

## 9. 배포 전 체크리스트

- [ ] `HF_TOKEN`이 Space Secrets에 등록됐고 **write** 권한인지
- [ ] Dataset repo 이름이 `app.py`의 `REPO`와 정확히 일치하는지
- [ ] `setter.call` 패턴을 썼는지 (§3.3) — 안 쓰면 빈 문자열이 조용히 넘어간다
- [ ] 업로드 실패해도 다운로드 버튼이 뜨는지 실제로 네트워크 끊고 테스트
- [ ] 테스트 파일 2개가 다른 이름으로 저장되는지 (덮어쓰기 아닌지)
- [ ] JSON 용량이 3MB 미만인지
- [ ] 전체화면 진입/이탈 시 좌표가 어긋나지 않는지
- [ ] 참가자 ID 중복 입력 시 동작
- [ ] `error_x/error_y` 부호를 산점도로 눈으로 확인
- [ ] 주 지표(성공률)를 문서에 적어뒀는지

## 10. 기존 코드에서 가져올 것 / 버릴 것

**가져올 것** — `experiment/`의 궤적 기록, 시행 루프, 전체화면 처리, JSON 내보내기

**호출하지 않을 것** — `error_decomposition.py`(회전), `feature_extraction.py`, `train_model.py`(릿지), 게이팅, σ/gap config

**삭제하지 말 것** — 위 코드는 최종 보고서에서 "궤적 기반 예측을 시도했으나 교차검증 R²가 3%였다"로 한 절을 차지한다. 단순한 방법을 고른 근거가 된다.
