# 마우스 보정 실험 v3 — 실행 가이드

`실험앱_계획서_v2(1).md`(구현 계획서 v3)를 실행하는 웹앱 + 분석 스크립트.
이 문서는 "무엇을 만들었는지"보다 **어떤 순서로 실행하는지**에 집중한다.

> **실험 질문 하나** — 개인별 클릭 편향을 학습해 빼주면 정확도가 오르는가?
> 그 이득은 개인화 때문인가?
>
> **주 지표는 성공률이다.** 데이터를 보기 전에 확정했다(계획서 §6.3). 오차 거리·반복측정
> ANOVA는 보조 지표이며, 성공률이 아니라 오차 거리로 결론을 바꿔 쓰지 않는다.

## 어느 쪽으로 갈지 — A안 / B안

| | 서버 저장 | 언제 |
|---|---|---|
| **A. 로컬 실행** | ✗ (브라우저 다운로드 폴더) | 8명을 한 PC에 모을 수 있을 때 — **권장** |
| **B. Gradio Space + HF Dataset** | ✅ | 원격·여러 장소 |

A안이면 인터넷도 배포도 토큰도 필요 없고, 마우스·화면이 자동으로 통제된다.
이 연구에서 그건 편의 문제가 아니라 타당도 문제다(계획서 §7).

### A안 실행

```bash
cd new2
python -m http.server 8000
```

브라우저에서 `http://localhost:8000/static/` 접속.
**`file://` 로 열지 말 것** — 마크업 조각을 `fetch` 로 읽으므로 막힌다.

점검용 축소 모드는 `?dev=1` (`http://localhost:8000/static/?dev=1`).
워밍업 4 + 본시행 20회로 줄어들고, 내보낸 JSON에 `dev_mode: true` 가 박힌다.

### B안 배포

1. HF에서 **private Dataset repo** 생성 (예: `계정/mouse-exp-data`)
2. Settings → Access Tokens → **write 권한** 토큰 발급
3. Space(Gradio SDK, CPU Basic) 생성 → 이 폴더의 `app.py` · `requirements.txt` · `static/` 업로드
4. Space → Settings → Variables and secrets 에 등록
   - `HF_TOKEN` = 발급한 write 토큰 (**secret**)
   - `HF_DATASET_REPO` = `계정/mouse-exp-data` (variable)

`app.py` 는 repo 이름을 코드에 박지 않고 환경변수에서 읽는다(오타 한 번에 데이터가
사라지는 것을 줄이려고). 환경변수가 없으면 업로드만 실패하고 실험은 정상 진행되며,
완료 화면에 "환경변수 ○○ 가 없습니다 + 다운로드하세요" 가 표시된다.

## 실행 순서

### 0. 실험 전 자체 점검 (한 번)

```bash
cd new2
node tools/selftest.mjs          # 시퀀스·기하·집계·스키마 정합
python tools/test_app_save.py    # app.py 의 저장 경로 (B안으로 갈 때)
```

`selftest.mjs` 는 브라우저 없이 순수 로직만 검사한다(56개 검사). 특히 **experiment.js /
make_dummy.py / analyze.py 세 파일의 시행 레코드 키가 일치하는지**를 본다 — 한쪽만 고치면
실험을 다 하고 나서 분석이 안 도는 사고가 난다.

DOM 단위로 실제 클릭까지 흉내내 완주시켜 보려면(선택):

```bash
npm install jsdom                                     # 아무 폴더에서
export JSDOM_PATH=<...>/node_modules/jsdom            # PowerShell: $env:JSDOM_PATH = "..."
node tools/e2e-jsdom.mjs            # 축소 모드 24시행 + 무응답 + 전체화면 이탈
node tools/e2e-jsdom.mjs --abort    # 중단하고 저장 경로
node tools/e2e-jsdom.mjs --sizing   # 모드 A
node tools/e2e-jsdom.mjs --full     # 620시행 완주 (약 3분)
```

가상 마우스로 전 시행을 클릭해 나온 JSON의 부호 규약·거리·방향·궤적 형식·타이밍을
검사한다. 함께 확인되는 경로:

- **Gradio 브리지(§3.3)** — 실제 `#payload textarea` 를 놓고, 값이 빈 문자열로 넘어가지
  않는지 본다(이 한 줄 때문에 며칠 날리는 사고를 자동으로 잡는다)
- **전체화면 이탈** — 진행 중이던 시행만 버리고 다시 제시하는지, 번호가 비지 않는지
- **무응답(3000ms)** — `click`·`rt_ms`·`error_*` 가 `null`, `no_response: true` 로 남고
  본시행 수에 포함되는지
- **중단하고 저장** — 여기까지의 시행만 `aborted: true` 로 담기는지
- 완료 화면 다운로드 버튼과 `localStorage` 백업

### 1. 분석을 먼저 돌려본다 (계획서 §8-3)

실험 다 하고 분석이 안 도는 스키마를 발견하는 게 최악이므로, 더미 데이터로 §6을 먼저 통과시킨다.

```bash
cd new2/analysis
python make_dummy.py --out ../data_dummy                 # 8명, 개인차 있음
python analyze.py ../data_dummy --figures ../figures_dummy
# → "C > A 그리고 C > B → 보정이 되고, 개인화가 필요하다" 가 나오면 파이프라인 정상

python make_dummy.py --out ../data_dummy_flat --individual-sd 0
python analyze.py ../data_dummy_flat                     # 개인차가 없을 때의 갈래도 확인
```

### 2. 본인들이 먼저 완주한다 (계획서 §8-6, 건너뛰지 말 것)

참가자 8명을 모아놓고 버그를 발견하면 되돌릴 수 없다. 연구자 2명이 각각 모드 B를
600회 완주해서, 파일이 실제로 남고 §6 분석에 그대로 들어가는지 확인한다.

### 3. 모드 A — 버튼 크기 확정 (참가자 2~3명)

설정 화면에서 참가자 ID 입력 → **모드 A** 선택 → 시작 (워밍업 10 + 본시행 100회,
후보 8/12/16/24/32px 각 20회). 완료 화면에서 JSON 다운로드.

2~3명분이 모이면 설정 화면 → **모드 A 결과 집계** → 파일 전부 선택 → 집계 실행.
`logit(성공) = a + b·ln(크기)` 를 적합해 **성공률 65% 지점의 크기 1종**을 산출한다.

- **한 명만 하고 넘어가지 말 것** — 이 크기는 전원 공통으로 쓴다. 한 사람 손에 맞추면
  다른 참가자의 난이도가 어긋난다(경고가 표시된다).
- *관측 범위 밖 외삽* 경고가 뜨면 그대로 쓰지 말고 후보 크기를 넓혀 모드 A를 다시 돈다.

"이 크기를 모드 B에 적용" 을 누르면 설정 화면의 버튼 크기 칸이 채워진다.
기록용으로 집계 결과 JSON도 받아 둔다.

### 4. 모드 B — 본실험 (8명 전원)

참가자 ID 입력 → **모드 B** → 버튼 크기(3에서 정한 값) 확인 → 시작.
워밍업 20 + 본시행 600회, 약 25분. **반드시 한 세션에** 끝낸다.

- 100회마다 휴식 화면이 뜨고 참가자가 직접 재개한다.
- **앞 400회 = 학습, 뒤 200회 = 평가.** 참가자에게 알리지 않고 화면상 구분도 없다.
- 완료 화면에서 JSON 다운로드 → `new2/data/` 로 옮긴다(A안). B안이면 Dataset repo의
  `raw/` 에 쌓이므로 한꺼번에 내려받는다.

시작 화면이 자동으로 점검하는 것: 창 크기(`≥1200×800`, 전체화면 진입 직후 실측),
확대율 100%(전체화면 진입 전 추정), 입력 장치 선택. 사람이 챙겨야 하는 것:
**마우스 가속 끄기, 8명 전원 같은 PC·같은 마우스, 트랙패드 금지.**

### 5. 분석

```bash
cd new2/analysis
python analyze.py ../data --out ../data/result.json --figures ../figures
```

출력 구성

| 절 | 내용 |
|---|---|
| [1] | **부호 규약 자체 점검** — 본인 벡터를 빼면 학습 구간 평균 오차가 줄어야 한다 |
| [2] | 참가자별 편향 벡터, 남의 편향 벡터, timeout·무응답 수 |
| [3] | 편향의 개인차가 실재하는가 — 참가자 간 SD vs 추정오차 SE, 일원배치 ANOVA |
| [4] | 세 조건(A/B/C) 성공률·평균 오차 |
| [5] | **주 검정** Cochran's Q → 사후 McNemar 정확검정 + Bonferroni |
| [6] | 보조 — 오차 거리 대응표본(t/Wilcoxon, Cohen's d), 반복측정 ANOVA |
| [7] | 계획서 §6.4 판정 |

그림 3종: `error_scatter.png`(부호 눈으로 확인), `success_by_condition.png`,
`bias_vectors.png`(공통 몫 vs 개인차 몫).

세 갈래 모두 결론이다. **C ≈ A(❌)도 보고 가치가 있다** — 연구계획서 1장의 전제가
틀렸다는 뜻이니까.

## 계획서에서 확정·조정한 것

구현하면서 계획서와 어긋나거나 비어 있던 지점, 그리고 그 처리.

### 1. 시작 버튼을 화면 정중앙에 고정할 수 없다 (§4.3 ↔ §7)

`중앙 + 450px + 상하 방향`은 §7의 `innerHeight ≥ 800` 기준과 양립하지 않는다.
높이 800이면 중앙 400 − 450 = **−50**, 실제 연구 환경인 1440×900에서도 위쪽 목표가
y=0에 걸린다. 거리 450px 고정과 4방향은 분석의 뼈대라 건드릴 수 없으므로,
**시작 버튼을 해당 축으로 필요한 최소량만 민다**(1440×900에서 ±14px).

- 가로 시행은 정확히 화면 중앙에서 시작한다(밀 이유가 없다).
- 밀렸는지는 시행마다 `start_shifted` 로 기록되고, 완료 화면에도 건수가 표시된다.
- 어떤 방향으로도 배치가 불가능한 화면이면 시작을 막는다.

### 2. 스키마에 `main_index` 를 추가했다

계획서 §5의 `index` 만으로는 "앞 400 / 뒤 200"을 자를 기준이 애매하다(워밍업 20회가
앞에 있으므로). `index` 는 세션 전체 순번, `main_index` 는 본시행 내 순번(워밍업은
`null`)으로 나눴다. 분석은 `main_index < config.train_split` 으로 학습 구간을 정한다.
전체화면 이탈로 버린 시행이 번호를 비우지 않는지 e2e 시험이 확인한다.

### 3. 방향 규약을 §5 예시에 맞췄다

계획서 §5의 예시가 `direction_deg: 90` 에서 `target.y(200) < start.y(650)` 이므로
**90°는 위**다(`dy = −sin θ`). 화면 y축은 아래로 증가하므로 이 부호를 놓치면 위아래가
뒤집힌다. `config.direction_convention` 에 문자열로도 박아 둔다.

### 4. 방향은 100회 블록마다 균등 배분한다

600회를 통째로 섞으면 앞 400과 뒤 200의 방향 구성이 우연히 달라질 수 있다. §6은 학습
벡터를 평가 시행에 그대로 적용하므로, 그 경우 "개인 편향"이 아니라 "방향 구성 차이"를
재게 된다. 블록(100회)마다 4방향 25회씩 넣으면 학습 400·평가 200 어느 쪽으로 잘라도
방향이 정확히 균형이고, 피로 효과도 방향에 고르게 퍼진다.

### 5. 버튼 크기는 파일이 아니라 화면에서 넘긴다

모드 A 집계 결과를 config 파일로 주고받는 경로(구버전 방식)는 실패 지점이 하나 더
늘어난다. 집계 화면의 "모드 B에 적용" 버튼이 설정 화면의 숫자 칸을 채우는 방식으로 했다.
기록용 집계 JSON은 따로 받을 수 있다.

### 6. 확대율 검사는 전체화면 진입 **전**에만 가능하다

전체화면에서는 `outerWidth`·`innerWidth` 가 같은 CSS px로 보고되어 확대율이 항상 1로
나온다. 그래서 설정 화면(창 모드)에서 재고 그 값을 `environment.zoom_estimate` 에
기록한다. 창 크기 기준은 반대로 전체화면 진입 직후 실측으로 검사해 미달이면 막는다.

### 7. 트랙패드는 경고 + 명시적 확인

§7은 "트랙패드 금지"이자 표에서는 "경고"다. 선택하면 붉은 경고가 뜨고, 확인란을
체크해야 시작 버튼이 열린다. 값은 `environment.input_device` 로 남고, 분석 스크립트가
`mouse` 가 아닌 데이터를 경고로 표시한다.

### 8. 전체화면 이탈 시 해당 시행을 버린다

이탈·재진입 사이에 뷰포트가 바뀌면 이미 계산한 좌표가 낡은 값이 된다. 반쯤 진행된
시행을 이어받는 대신 버리고 같은 조건으로 다시 제시한다(`session_events` 에 기록).
같은 화면에서 "중단하고 저장"도 가능하다 — 여기까지의 시행은 그대로 내보낼 수 있다.

### 9. 다운로드 외에 브라우저 백업을 하나 더 둔다

업로드도 다운로드도 실패할 수 있고 참가자를 다시 부를 수는 없다(§3.4). 완료 시
`localStorage` 에도 백업하고, 설정 화면의 "이전 세션 복구" 에서 다시 받을 수 있다.
용량을 넘기면 궤적을 떼고 저장한다 — 궤적은 이번 분석에 쓰지 않으므로(§4.3) 떼어낸
백업으로도 §6은 전부 돌아간다.

### 10. 파일명·ID 위생을 두 곳에서 같은 규칙으로

`app.py` 의 `isalnum()` 필터는 한글·한자도 통과시킨다(파이썬 `str.isalnum()` 은
유니코드 기준). 실험 화면이 ID를 ASCII로 제한하므로, 서버도 같은 ASCII 규칙을 써서
파일명 인코딩 문제를 아예 만들지 않는다. `tools/test_app_save.py` 가 `../../etc/passwd`
같은 입력까지 확인한다.

### 11. 시간 압박 표시줄을 남겼다

750ms 소프트 제한이 보이지 않으면 참가자가 버튼 위에서 느긋하게 미세조정해버려
측정하려는 오차 자체가 생기지 않는다. 화면 맨 위 5px 띠로 표시하고
`pointer-events: none` 이라 위쪽 목표와 겹쳐도 클릭이 통과한다.

### 12. 궤적 샘플링은 mousemove + requestAnimationFrame

§4.3은 "mousemove를 전부 기록"이라고 적었지만, 구현은 mousemove로 최신 좌표를 갱신하고
프레임마다(rAF) 한 점씩 쌓는다. 이유는 두 가지다.

- **커서가 멈춰 있는 구간도 샘플이 남는다.** 사람은 목표에 커서를 세운 뒤 클릭하며
  그 정지가 80~100ms 이어진다(`new/` 의 test01 관측). 이벤트만 받으면 이 구간이 빈다.
- **§3.5의 용량 추정(시행당 약 75샘플)과 맞는다.** 실측 샘플 간격 중앙값 8ms(125Hz)로,
  브라우저가 mousemove를 프레임 단위로 합치는 것과 결과가 거의 같다.

완료 화면과 각 시행 레코드에 실제 샘플 간격 중앙값이 남으므로, 세션마다 실제 표본율을
확인할 수 있다.

### 13. Gradio 통로 컴포넌트는 CSS로 감춘다

`gr.Textbox(visible=False)` 는 Gradio 버전에 따라 DOM에 렌더링되지 않을 수 있고, 그러면
JS가 `#payload` 를 못 찾아 **조용히** 저장이 안 된다(§3.3이 경고하는 것과 같은 종류의
사고다). 컴포넌트는 살려 두고 `display: none` 으로만 감춰 DOM에 반드시 존재하게 했다.

### 궤적에 대해

이번 분석에는 **쓰지 않는다**(§4.3). 그래도 `[[t, x, y], ...]` 숫자 배열로 기록은 남긴다
— 보고서에 "궤적 기반 예측도 시도했으나 설명력이 3%였다"(`new/` 의 test01 결과)를 쓸
재료이자, 나중에 다시 볼 여지다. 좌표는 소수점 첫째 자리로 반올림해 용량을 절반 이하로
줄였다(620시행 약 1MB).
